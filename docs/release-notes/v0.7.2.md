## infoclock32 0.7.2

Weather for more than one place. Give the clock a few named locations and it shows each one in turn, with Open-Meteo (no account) or OpenWeatherMap, or a mix of both. The `ow_*` keys now have `weather_*` names, and the clock tells you, on the web page and on the LED, when your config still uses a name that is going away.

### Highlights

- **Several weather locations.** Up to 4 places, shown in turn. Each place is a set of keys named after a short id (lowercase letters and digits):

  ```
  weather_crozet_lat=46.2820
  weather_crozet_lon=6.0105
  weather_crozet_name=Crozet
  weather_geneve_lat=46.2022
  weather_geneve_lon=6.1457
  weather_geneve_name=Geneve
  ```

  Use `_lat` / `_lon` for Open-Meteo (free, no API key) or `_city_id` for OpenWeatherMap, `_name` for the label that scrolls, and an optional `_provider` (`owm` or `open-meteo`) to mix backends. Locations are found by scanning the config and are shown in alphabetical order of their ids. Each one has its own schedule and retry backoff, so one failing place does not hold up the others.
- **New placeholders per location:** `{weather_<id>_temp}`, `{weather_<id>_desc}` and `{weather_<id>_id}`, for example `{weather_crozet_temp}` in a custom message.
- **Warnings for deprecated config.** The web home page and `/edit` show an amber box listing every deprecated key still in use (values are never shown), and the LED scrolls "Check your config" now and then. `config_warn_interval_min` sets the interval (default 60 minutes, `0` = off); the first reminder comes 10 minutes after boot and never while night mode is active. The text exists in all seven display languages.
- **Shared weather settings.** `weather_provider` (`auto`, `owm`, `open-meteo`), `weather_api_key` and `weather_interval_min` (10–1440 minutes, default 30) apply to every location. `auto` picks OpenWeatherMap for a place that has a city ID while an API key is set, and Open-Meteo otherwise.

### Deprecations (removed in 0.9.0)

Everything keeps working unchanged for now; the clock only warns.

| Deprecated | Use instead |
|---|---|
| `ow_api_key` | `weather_api_key` |
| `ow_city_id` | `weather_<id>_city_id` (single location: `weather_city_id`) |
| `ow_interval_min` | `weather_interval_min` (now applies to every location) |
| `{weather_temp}`, `{weather_desc}`, `{weather_id}` | `{weather_<id>_temp}` etc. They mirror the first location until removal. |
| `temp_sensor`, `temp_interval`, `temp_display`, `temp_decimals`, `temp_show_interval`, `temp_hold_s` | Already ignored since the multi-sensor rework; now flagged in the warnings too. Use `sensors` / `sensor_*`. |

The single-location keys `weather_lat` / `weather_lon` / `weather_name` / `weather_city_id` still work while no `weather_<id>_*` location exists. Once one does, they are ignored, and the web page says so.

### Under the hood

- The weather task re-reads the config on every pass, so adding, removing or renaming a location in `/edit` takes effect without a reboot.
- Requests are made one at a time, as before, so TLS handshakes never overlap. Between two scrolls there is a pause of at least 20 s.
- The housekeeping task stack grew from 4 KB to 5 KB for the warning check.
- `weather_api_key` is treated as a secret: masked in logs and in `/api/runtime`, like `ow_api_key` was.
- New pure, host-tested headers (`weather_locations.hpp`, `deprecated_keys.hpp`, `config_view.hpp`) with their own tests and prototype scenarios for two named locations and for the warning banner.

### Upgrading

- OTA is enough: upload the plain `infoclock32-v0.7.2-<board>.bin` on `/update`. The partition layout is unchanged, so `config.txt` is kept.
- For a fresh board or a web flasher, use the `-merged.bin` at offset `0x0`.
- Nothing needs to change right away. When you are ready, rename `ow_api_key` to `weather_api_key` and give each place its own `weather_<id>_*` keys (see `config.example.txt`).
- Verified on hardware: ESP32-C3 only. `esp32dev` was built and host-tested; the weather task and its stack sizes have not been measured on the other boards.
